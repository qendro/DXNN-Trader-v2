PCI vs PLI: Inputs the Agent Sees

mode: PLI

PLI feeds the NN a sliding window of recent closing prices with length HRes (e.g., 5, 10, 20, 50, 100). This is a 1D vector.

[p, p, ..., p, p]

Internals sensor adds: [position (-1/0/1), entry, percentage_change].

PCI converts the sliding price list into a candlestick chart plane with resolution HRes × VRes, using trinary encoding per cell:

  • 1 body (between open & close)
  • 0 wick (between low & high, outside the body)
  • -1 background
1 (body) 0 (wick) -1 (bg)

Single-candle encoder

When do I prefer PCI vs PLI?

PCI (geometry-sensitive substrates) generalized more consistently in the chapter’s benchmarks; PLI had occasional higher spikes but was short-lived. PCI’s coordinate-based substrate helps avoid memorizing exact values, focusing on shapes/patterns.

Account Mechanics & P/L Calculator

Formulas

  • Change = Close - Entry
  • PChange = (Change / Entry) × 100
  • Profit = Action × Change × Units (Action ∈ {-1,0,1})
  • NAV = Balance + Unrealized_PL
  • Entry includes spread: Entry = Quote + Spread × Action

Default: start balance $300; open orders buy $100 with 50× leverage (units ≈ 5000/Entry).

Neural Topologies

PLI (direct-encoded) experiments

Sliding-window inputs of length: 5102050100. Each agent also receives fx_internals. Evolution may add recurrent connections; high performers often had substantial recurrence.

PCI (substrate-encoded) experiments

4D substrate, Jordan recurrent:

  • Input hyperlayer at K=-1: fx_PCI plane, fx_internals, plus recurrent copy of output
  • Hidden hyperlayer at K=0: 5×5
  • Output hyperlayer at K=1: 1×1 (mapped to short/hold/long)
Activation functions enabled

[tanh, gaussian, sin, absolute, sgn, linear, log, sqrt]

Benchmark Protocol

  • Data: EUR/USD 15-min closes, 1000 ticks (Nov 5–20, 2009)
  • Training: first 800 ticks; Generalization: next 200 ticks
  • Start balance: $300; spread: 0.000150; leverage: ×50; open position with $100 (units ≈ 5000/Entry)
  • Population size: 10; Evaluations per run: 25,000; Runs per experiment: 10
  • Generalization test cadence: every 500 evaluations
  • Fitness: Net Asset Value at end of evaluation; halt early if NAV < $100

Outcome (high level): PCI generalized more consistently; PLI had brief higher spikes but tended to overfit. High vertical resolution (×20) often helped PCI; among PLI, windows 5 and 100 were most stable.

DXNN Process Architecture: Cortex ↔ Neurons ↔ Sensors/Actuators ↔ Scape ↔ Exoself

This mirrors the book’s message-passing design: exoself supervises evolution; cortex orchestrates sense–think–act; sensors/actuators bridge to scapes; neurons are independent processes with recurrent links.

Signal flow (canonical 1–9)

  1. Exoself spawns NN and idles.
  2. Cortex sends {CxPid, sync} to sensors (call to action).
  3. Sensors request data from scape with {SPid, ControlMsg}; scape replies {ScPid, percept, Vector}.
  4. Sensors (optionally) preprocess, then fan-out vectors to connected neurons via {InputPid, forward, Input}.
  5. Neurons compute; activations flow to actuator inputs.
  6. Actuators aggregate outputs; send {APid, ControlMsg, Output} to scape.
  7. Scape executes action; returns {ScPid, Fitness, HaltFlag} to actuator.
  8. Actuators forward {APid, sync, Fitness, HaltFlag} to cortex; cortex accumulates fitness and checks halts.
  9. If no halt → loop to step 2; if halted → cortex notifies exoself for evolutionary decision.

Design reason: scape talks back via actuators so cortex can halt synchronously and avoid sensors advancing after termination.

Neuron Lifecycle & Exoself Controls

Each neuron is its own process with inbox and recurrent outputs on init. Exoself perturbs, backs up, restores, and resets neurons between evaluations.

  • Init: neuron receives Input_PIdPs=[{InputPid, Weights}], AF/PF/Aggregator; emits default signals to recurrent outputs; enters main loop.
  • Main messages: {InputPid, forward, Input}; {ExoSelf, weight_backup}; {ExoSelf, weight_restore}; {ExoSelf, weight_perturb, Spread}; {ExoSelf, reset_prep} → {ExoSelf, reset}.
  • Exoself evaluation loop: on evaluation_completed, if new fitness ≤ best → restore; else → backup; optionally select subset of neurons to perturb; reactivate cortex.
Tip: perturbation probability ~ 1/sqrt(TotalNeurons). Recurrent buffers must be flushed on reset to avoid stale state.

Glossary (DXNN terms)

Cortex

Coordinator that synchronizes sensors, aggregates fitness/HaltFlag from actuators, and communicates evaluation completion to exoself.

Exoself

Evolutionary controller that perturbs, restores, and backs up neuron weights; starts/stops evaluations and tracks best fitness.

Scape

Environment/simulator process (here: fx_sim) that executes actions, produces sensory vectors, and reports Fitness + HaltFlag.

Sensors

Bridges from scape → NN. On sync, request data (ControlMsg) and fan-out vectors to neurons.

Actuators

Bridges from NN → scape. Collect outputs, postprocess, trigger scape actions, and forward fitness/halts to cortex.

Neurons

Independent processes with input lists and weights; accept forward signals; support recurrent outputs and exoself control messages.

    Quick Notes & Tips

    • Trade signal is derived by thresholding NN output: <-0.5 = -1 (short), between -0.5..0.5 = 0 (close/hold), >0.5 = 1 (long).
    • Use PCI when you want geometry-aware pattern recognition (candles, wicks, bodies). Use PLI for traditional feature vectors.
    • Termination: advance one tick per access; end when index hits end of table or NAV dips below $100.
    • Real-world deployment requires connecting the actuator to a live broker API and mirroring the sim’s spread/leverage rules.
